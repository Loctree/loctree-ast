# Codex Manifest Protocol for MCP

## Introduction
The **Codex Manifest Protocol** (often referred to as "stateful chunking") is a novel pattern implemented within the `loctree-mcp` server. Its purpose is to deliver the massive, high-fidelity context generated by `loct context` into the narrow starting context windows of AI agents, without truncating critical architectural or risk data.

Before this protocol, `loctree-mcp` relied on a "slim mode" which aggressively clamped lists (e.g., maximum 5 structural dependencies) to fit into single JSON payloads. This lossy approach resulted in context starvation and AI hallucinations. 

The Codex Manifest Protocol solves this by forcing the AI agent to paginate through the exact `ContextPack` data sequentially, reading the ground truth in distinct logical sections, and ultimately verifying completion via a cryptographic receipt.

## The `loct context` Foundation
At the heart of the MCP delivery is the core `loctree` CLI command: `loct context`. 
When invoked, `loct context` (or internally `compose_context_pack`) builds a comprehensive `ContextPack` containing the following layers of the codebase:

1. **Identity & Core:** Schema version, project identity.
2. **Risk & Action:** Hotspots, dirty worktree markers, safe next commands, and verification gates.
3. **Authority:** Provenance labels (RepoVerified, AicxOperator, SemanticGuess, etc.).
4. **Structural (Cut 4/T1):** Holographic file data, exported symbols, reverse-dependency consumers, and entrypoints.
5. **Runtime (Cut 4/T2):** Semantic facts, reachability, environment variables, Tauri bridges, and framework hints.
6. **Memory (Cut 5/T1 - Optional):** AICX Intent history, tasks, and past architectural decisions.

The `loctree-mcp` server generates this massive payload once per request chain and then parcels it out using the Manifest Protocol tools.

## The Protocol Tools
To interact with the context pack, the `loctree-mcp` server exposes four specific MCP tools.

### 1. `context`
**The Entrypoint.**
When an agent calls `context`, the server generates the full pack but only returns the `core` section (Identity, Risk, Action, Authority). 
Crucially, it assigns a `session_id` and returns a `next_cursor` alongside an `"incomplete"` status and an advisory warning.

**Payload Excerpt:**
```json
{
  "session": "ctx_1714732800",
  "status": "incomplete",
  "chunk": 1,
  "section_group": "core",
  "sections_missing": ["structural", "runtime"],
  "next_cursor": "ctx_1714732800|/project/path|structural|0",
  "advisory": "CRITICAL: Context loading is incomplete. Do not make broad architectural decisions until required sections are loaded. Call context_next with the provided cursor."
}
```

### 2. `context_manifest`
**The Metadata Endpoint.**
If an agent needs to know the topology of the context before retrieving it, `context_manifest` returns a schema description of all available chunks and their IDs (`core`, `structural`, `runtime`, `memory`).

### 3. `context_next`
**The Stateful Iterator.**
The agent passes the `next_cursor` provided from the previous step. The server unpacks the cursor (`session_id|project_path|section|with_aicx_flag`) and yields the corresponding data chunk.
- If the cursor points to `structural`, it yields the structural slice and provides a new cursor for `runtime`.
- If the cursor points to `runtime`, it yields the runtime slice and provides a new cursor for `memory` (or `receipt`).

**The Receipt Marker:**
When the final section is loaded, the cursor resolves to the `receipt` section. The server hashes the `session_id` and `project_path` using **SHA-256**. 
It returns a payload with the status `"complete"` and a `context_receipt` object. This cryptographic marker ensures the agent loop acknowledges full ingestion of the context pack before beginning architectural synthesis.

**Receipt Payload:**
```json
{
  "session": "ctx_1714732800",
  "status": "complete",
  "context_receipt": {
    "sections_loaded": ["identity", "risk", "action", "authority", "structural", "runtime"],
    "sections_skipped": ["memory"],
    "aicx": "disabled",
    "sha256": "4f53cda18c2baa0c0354bb5f9a3ecbe5ed12ab4d8e11ba873c2f11161202b945"
  }
}
```

### 4. `context_section`
**Direct Refresh.**
For agents that need to re-read a specific chunk (e.g., retrieving `runtime` again mid-session without resetting the entire chunking sequence), the `context_section` tool accepts a specific section ID and returns it immediately. The status is marked as `"partial_direct_load"` to distinguish it from the strict onboarding sequence.

## Conclusion
By shifting from "lossy truncation" to "stateful pagination", the Codex Manifest Protocol ensures that AI assistants never start a complex task with incomplete dependency or risk maps. The strict sequence and explicit receipts align with `loctree`'s philosophy: **Runtime truth beats theoretical correctness.**
